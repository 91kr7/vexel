A Cache Between Us and Docker

Today every browser window asks Docker directly, over and over. This document proposes one change: a background task reads Docker on its own schedule and keeps the answer in memory. The list routes then read that memory. The client does not change at all.

1 The problem, in numbers

One window is open. Nobody clicks anything. No heavy screen is selected. This is what the application does anyway, every minute:

browser → server 116 /min

Five lists every 3 seconds, plus connection status and contexts.

server → Docker 212 /min

Almost twice as many. The reason is in section 2.

processes started 64 /min

Docker CLI commands, not network calls.

with two windows ×2

Nothing on the server joins two clients that ask for the same list.

This runs when the window is minimised. It runs at night. It runs on screens that do not show any of this data.

2 Why the two numbers are different

The server looks like a pipe, but it is not. One browser request becomes several Docker calls. This is the main thing to understand before reading the design.

Two calls cost much more than the others.

/system/df is the heaviest endpoint Docker has. It walks the whole storage. We call it every 3 seconds, only to show the size of each volume. It has no cache on our side and no cache on Docker's side: eleven reads, 3 seconds apart, all took about 73 ms.

The images list is the only one that gets slower as the user keeps more images. We ask Docker to inspect every image, every 3 seconds, to read a value like linux/arm64. That value can never change for a given image ID.

3 The design

Add one background task on the server. It reads Docker on its own schedule and stores the result in memory. The list routes read that stored value. They never call Docker directly any more.

Today

Browser asks the server every 3 seconds.

Server calls Docker and waits.

Docker answers.

Two windows means two of everything. The client sets the rate at which Docker works.

Proposed

Browser asks the server every 3 seconds. No change.

Server answers from memory at once.

A background task refreshes that memory on its own schedule.

Two windows read the same memory. The server sets the rate at which Docker works.

The grey path is what the browser sees. It is the same as today, but it never waits for Docker. The orange path is new, and it is the only path that reaches Docker.

4 Four rules that make it work

A cache with only a timer would be worse than what we have today. These four rules are not optional.

R1

Always answer from the cache, even while it is refreshing

The client must never wait for Docker. If a refresh is running, we return the previous value. The only exception is the very first request, when the cache is still empty.

R2

Refresh on Docker events, not only on the timer

If we refresh only every N seconds, then after the user stops a container the screen shows the old state for up to N seconds. That is worse than today. The fix is cheap: the server already keeps an open connection to Docker's event stream. When an event arrives, we mark the cache as old and refresh at once. We group events that arrive together, using a short delay of about 750 ms, so a burst becomes one refresh.

R3

Stop refreshing when nobody is looking

A task that runs for ever would call Docker even when no browser is open. Today that does not happen. We do not need a new protocol to fix this: the client's own request is the signal. If nobody has asked for the volume list in the last minute, we stop refreshing it. The next request starts it again. Close the browser and everything stops by itself.

R4

Our own write operations mark the cache as old immediately

When the user removes a volume through the application, the route that removes it marks that cache as old. We do not wait for the timer and we do not wait for the event. The user must see the result of their own action at once.

One more rule about failures. If Docker cannot be reached, the cache keeps the last good value and the time it was read. The route can then return that value and say how old it is. The container statistics code already does this: it marks data as old after 30 seconds instead of showing it as fresh.

5 How often the background task reads Docker

The client keeps its current intervals. The table below is only about the background task. Two columns matter: the timer, and what makes it refresh earlier.

The timers can be long because rule R2 covers the normal case. The timer is a safety net. It exists for the things Docker does not announce, and for the case where the event connection is lost.

Two rows deserve a note.

Volume sizes. The size of a volume is the slowest changing value in the application, and it is the most expensive one to read. Today they share one request with the volume list, so they share its 3-second interval. Splitting them is the single largest saving in this document. The application already knows this: the disk usage screen does not poll /system/df at all, and its comment says why.

CLI versions. Which CLI programs are installed cannot change while the server is running. This is not a question of interval. The value should be read once.

6 What we do not change

  • The client. No hook changes, no screen changes. The hooks keep the same shape and the same intervals.
  • Detail views (one container, one volume, one network, one image). They keep reading directly, with no cache on the server. This is a decision, not an oversight: a detail view shows one object, it is open one at a time, and the data must be exact.
  • Live streams: logs, container statistics, build output, file transfers. They are already correct and this document does not touch them.
  • The Docker event stream. One connection, shared, with a backlog. It stays as it is, and the background task now uses it.
  • Swarm. It is being removed, so it is out of scope.

One small fix inside the detail views. They read again on any event of the same type, not only on events about the object on screen. So the detail of container A is read again when container B starts. The volume case is worse, because reading one volume also calls /system/df. This is a separate small change: the server must publish the object ID in the event, and the client must compare it.

During real work the difference is also large. Starting and stopping one container produces 9 Docker events. Today each event makes several lists read again, which is 11 extra Docker calls in about one second. With rule R2 the same burst becomes one refresh.

8 Risks

Risk 1 — the application feels slower. This happens if rule R1 or rule R4 is wrong. If the user stops a container and the row does not change immediately, we have traded speed for cost, which is a bad trade. Check this first, on the container list, before applying the design to the other lists.

Risk 2 — the safety-net timer is too long. If an event is lost, the user sees old data until the timer fires. With a healthy event connection this does not happen. This is why the timers above stay at 20–30 seconds, except where the data really does change slowly (images, contexts, volume sizes).

Risk 3 — one slow read blocks everything. Use one background task per kind of data, not one task that refreshes everything in sequence. Today a slow volume read delays only volumes. Do not lose that: a single blocked /system/df or compose ls must not freeze every list.

9 Suggested order of work

The first group is small, local, and independent. It does not need the cache and it already removes most of the cost. Doing it first also means that if the larger work stops halfway, the main benefit is already there.

1

Small independent fixes

Remember the platform of each image by image ID. Read the CLI versions once. Reuse the connection to Docker instead of opening a new one for every call — this is almost free on a local socket, but on a remote ssh:// context every call currently starts an ssh process. Group event bursts in the client hooks. Publish the object ID in events and filter the detail views with it.

2

The cache, for containers only

Build the cache, the timer, the event invalidation and the demand rule for one kind of data. Check risk 1 on a real screen before going further.

3

The remaining lists

Images, volumes, networks, Compose projects, contexts, builders. One background task each.

4

Split the volume sizes, then tune

Give /system/df its own long timer. Then adjust the timers while watching the application, because this is the part that is easier to judge by using it than by reasoning.

This design is based on a reading of the code on 27 August 2026. Intervals and constants were read at the source. Timings were measured on the development machine, three runs per command, median, on a daemon with 3 images and no Compose project. The event burst was measured on the real life cycle of a test container, which was removed afterwards. Counts per hour are arithmetic over the intervals, not observed traffic.
