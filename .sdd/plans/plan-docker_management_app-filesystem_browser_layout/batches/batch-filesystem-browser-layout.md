## What the implementer must not get wrong

- **The fix is not allowed to live at the call site.** Wrapping the band in a `Row` inside
  `FilesystemBrowser.tsx` is legal composition, closes the void, breaks no conformance rule and
  leaves the shared defect armed for the next surface. INT-1's direct-child assertion exists to make
  that implementation red; do not weaken it into "the gap is small".
- **Do not trade a 240px void for an unbounded one.** In a column, `flex-grow: 1` means the band
  absorbs every remaining pixel. The band's height is the height of its control, measured against the
  control and never against the number 240.
- **A maximum, not a height.** The elastic region must give the tree a definite bounded height when
  the content exceeds the cap, and must **not** stretch when it does not. Give the arrangement a
  height and the dialog is 85vh forever (INT-3 fails); let the region "grow to fit" and the tree
  stops virtualising (INT-1's bounded-mount assertion fails). Both failures are one decision apart.
- **The three sibling dialogs are not touched, however trivial it looks.** Once INT-8 exists, each is
  a two-line change — and each would make a regression on this batch unattributable. Their pixel
  constants are a recorded breach with a report of their own coming; INT-4 guards them and INT-13
  records them.
- **The container logs view is the other half of the band's contract.** It uses the band on the axis
  it was written for and is currently correct. If INT-2 cannot be made to pass without changing the
  logs view, stop and ask the orchestrator: the correction is wrong, not the check.
- **Geometry is never asserted in jsdom.** Every box there is zero, so a layout assertion in a unit
  test passes on any build, defect included. INT-5 and INT-6 assert contract and state only, and say
  so on the spot.
- **Report the numbers, not the verdict.** REQ-32 is satisfied by measurements: the gaps in px, the
  region's height at 720 and at 1000, the count of scroll containers in the body, the count of fully
  visible rows — before the fix and after it. "Before: failed" is not evidence on a layout defect.

## Verification

**Test runs in this batch are batch-scoped, in both phases (development and test).** What is run:

- `npm run lint`
- `npm run test:typecheck -w client`
- `npm run test -w client` — the client unit tests, which include the UI-conformance check
  (unmodified, and passing: REQ-23)
- this batch's own e2e specs, **each run on its own** (REQ-36): the new geometry spec,
  `container-logs.spec.ts`, `dialog-sizing.spec.ts`, `layer-explorer.spec.ts`, `image-diff.spec.ts`,
  `layer-efficiency-signals.spec.ts`, and — as this batch's evidence for REQ-16 and REQ-17 —
  `filesystem-browser.spec.ts` and `filesystem-browser-operations.spec.ts`, which are **expected to
  pass unchanged**; any edit either of them turns out to need is reported with its reason, since a
  layout fix should not move a selector.

**Neither phase launches the complete unit suite or the complete e2e suite.** The human has
instructed that both run **once, at the end of the whole five-report tranche**, on his own daemon; a
subagent starting a full run competes with him on that same daemon and fails in plausible-looking
places. If a change appears to need wider coverage than the list above, that is a question for the
orchestrator, not a reason to widen the run.

- INT-1 to INT-6 are run **before** INT-7 to INT-12 exist, and reported with the measurements they
  produced on the delivered build (REQ-32).
