**Order.** INT-1 to INT-5 are written and **run against this build first**, before INT-6 to INT-11

corrections, then the three feature files, then the documentation.

**The arithmetic this batch is built on**, so that no intervention re-derives it and none of it is
written as a literal at a call site: the column gap is the library's `--space-6` (24px); with a 360px
short-scalar minimum the count is `floor((W + 24) / 384)`, which gives **1 / 2 / 3 / 4 columns at
600 / 900 / 1300 / 1700px** of measured section width and puts the transitions at **744 / 1128 /
1512px** — the three the analysis states. The long-single-line minimum of 560px puts its second
column at 1144px. At the delivered 37px band step this clears every height ceiling with margin
(~185 / ~111 / ~74px against 214 / 148 / 115 for the image panel's nine, and against 238 / 165 / 128
for the container's ten), so **nothing in this batch may be bought out of the type, the padding or the
row height** (REQ-34).

## What the implementer must not get wrong

- **Do not put a number in a call site.** The likeliest wrong fix, named by the analysis: pass three
  columns on the image panel and ship the screenshot. It looks right on one monitor, gives ~180px
  cells on a laptop and leaves eleven screens untouched. INT-1(a) asserts four counts at four
  measured widths; a constant fails three of them.
- **Do not key it to the viewport.** The second-likeliest, and it reads correct in review because the
  human said "device size". INT-2 is written to fail it: two sections on **one screen at one instant**,
  one at full panel width and one at half of it, must show different counts.
- **Do not split the pair into label and value tracks.** `display: contents` or a subgrid over the
  label and value spans is the neatest-looking grid and is exactly the tabular arrangement the
  analysis rejected: it reads column-first to a screen reader and breaks the moment one value wraps.
  The row element stays the grid item. INT-5 asserts it at component level and INT-1(g) asserts the
  reading order in a real browser.
- **Three classes means three minima, not one number applied three times.** A 400-character
  `createdBy` in a 360px column is a different defect, not a fix. `History` gets no grid at all.
- **A minimum is not a width.** In a ~400px card a 560px minimum must degrade to the card's width,
  not push through it. That is the case the delivered `columns={2}` surfaces already fail, and
  recreating it would answer a wasted-space report with a clipping defect.
- **Nothing is measured in JavaScript.** No `ResizeObserver`, no layout read in an effect, nothing
  per frame. These sections sit in the scrolled main view of screens listing hundreds of objects, and
  the project's own performance rule is that the main view pays nothing.
- **Do not touch the five `columns={2}` surfaces**, however trivial the deletion looks once INT-7
  exists. Each would make a regression on this batch unattributable and would empty batch 2 of its
  content. INT-4 guards them; the temptation is named here so it is refused knowingly.
- **Do not touch the `Copy` controls.** bug-5 is the next report and one of these controls is visible
  in this report's screenshot. Moving or removing one here makes both reports unattributable.
- **Do not disturb bug-3.** `FilesystemBrowser.tsx` is expected to need no edit. If it does, report
  the reason; do not fold a second surface's layout into this batch.
- **Geometry is never asserted in jsdom.** Every box there is zero, so a layout assertion in a unit
  test passes on any build. INT-5 is contract and state only, and says so on the spot.
- **Report the numbers, not the verdict.** REQ-42 is satisfied by measurements: the counts at each
  measured width, the section heights at the three viewports, the label→value run on the `Created`
  band — before the fix and after it. "Before: failed" is not evidence on a layout defect.

## Verification

**Test runs in this batch are batch-scoped, in both phases (development and test).** What is run:

- `npm run lint`
- `npm run test:typecheck -w client`
- `npm run test -w client` — the client unit tests, which include the UI-conformance check
  (unmodified, and passing: REQ-37)
- this batch's own e2e specs, **each run on its own** (REQ-44): the image-panel geometry spec, the
  container-panel geometry spec, the consuming-screens sweep, the untouched-surfaces guard, and — as
  this batch's evidence for REQ-31 — the delivered `images.spec.ts`, `containers.spec.ts` and
  `filesystem-browser.spec.ts`, which are **expected to pass unchanged**; any edit one of them turns
  out to need is reported with its reason, since a layout fix should not move a selector.

**Neither phase launches the complete unit suite or the complete e2e suite.** The human has
instructed that both run **once, at the end of the whole five-report tranche**, on his own daemon; a
subagent starting a full run competes with him on that same daemon and fails in plausible-looking
places. If a change appears to need wider coverage than the list above, that is a question for the
orchestrator, not a reason to widen the run.

- INT-1 to INT-5 are run **before** INT-6 to INT-11 exist, and reported with the measurements they
  produced on the delivered build (REQ-42).
